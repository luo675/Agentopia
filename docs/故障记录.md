## 最终可用配置

```bash
vllm serve ~/models/Qwen3-8B-AWQ \
  --served-model-name Qwen/Qwen3-8B-AWQ \
  --port 8000 \
  --gpu-memory-utilization 0.85 \
  --max-model-len 16384 \
  --enable-auto-tool-choice \
  --tool-call-parser hermes
```

## 故障记录

### ❌ 故障 1：显存不足（NVML memory utilization）

**错误信息**：
```
ValueError: Free memory on device cuda:0 (10.77/11.94 GiB) on startup is less 
than desired GPU memory utilization (0.92, 10.98 GiB).
```

**根本原因**：
- 12GB 标签值 → 11.94 GiB 实际值
- Windows 桌面/WSL2 虚拟显示已占 ~1.9 GiB
- vLLM 默认 `--gpu-memory-utilization 0.92` 要求 10.98 GiB > 可用 10.77 GiB

**解决方案**：`--gpu-memory-utilization 0.85`

**影响**：KV cache 从 ~6GB 降到 ~5.2GB，单并发 + 16K 上下文完全够用

**日期**：2026-06-23

---

### ❌ 故障 2：FlashInfer 不支持 Blackwell (RTX 5070 Ti)

**错误信息**：
```
RuntimeError: Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist
```
后又出现：
```
#error "CUDA compiler and CUDA toolkit headers are incompatible, 
please check your include paths"
```

**根本原因**：
- vLLM 0.20+ 捆绑 FlashInfer，启动时 JIT 编译 CUDA 采样 kernel
- FlashInfer 0.6.x 的 CUB 库不支持 RTX 5070 Ti 的 Blackwell 架构 (`sm_120f`)
- 2026-06-23 时 FlashInfer 上游尚未发布 Blackwell 兼容版本
- pip 安装的 `nvidia-cuda-nvcc-cu12` 实际是 CUDA 13，与 FlashInfer 的 CCCL 不兼容

**尝试过的无效方案**：
- 安装 `nvidia-cuda-nvcc-cu12` — 版本不兼容
- 删除 nvcc 二进制 — 硬编码路径导致 `exit 127`
- 设置 `VLLM_USE_FLASHINFER=0` — vLLM 0.20+ 忽略此变量
- monkey-patch flashinfer → 太脆弱，不推荐

**最终解决方案**：降级到 vLLM 0.19.1

```bash
pip uninstall vllm flashinfer-python flashinfer-cubin -y
pip install vllm==0.19.1 -i https://pypi.tuna.tsinghua.edu.cn/simple
rm -rf ~/.cache/flashinfer
```

**vLLM 版本对照**：
| 版本 | FlashInfer | Blackwell 支持 | 可用 |
|------|:--:|:--:|:--:|
| 0.23.0 | 0.6.12 JIT | ❌ | ❌ |
| 0.22.1 | 0.6.11 JIT | ❌ | ❌ |
| 0.19.1 | 0.6.6 cubin | ✅ (预编译) | ✅ |

**影响**：PyTorch 原生采样替代 FlashInfer，token 选择慢 1-3ms，几乎无感

**日期**：2026-06-23

### ❌ 故障 3：KV cache 不足以服务 max_seq_len=40960

**错误信息**：
```
ValueError: To serve at least one request with the models's max seq len (40960),
(5.62 GiB KV cache is needed, which is larger than the available KV cache 
memory (3.18 GiB). Based on the available memory, the estimated maximum model 
length is 23152.
```

**根本原因**：
- 模型默认 max_seq_len = 40960
- 85% 显存可用 KV cache 仅 3.18 GiB（扣除模型 5.71 GiB + CUDA graph 0.35 GiB）
- 40K 上下文需要 5.62 GiB KV cache

**解决方案**：`--max-model-len 16384`（16K 上下文，KV cache 需求降到 ~2.2 GiB）

**日期**：2026-06-23

### ❌ 故障 4：请求 token 超出模型上下文限制

**错误信息**：
```
This model's maximum context length is 16384 tokens. However, you requested 
16384 output tokens and your prompt contains 2737 characters
```

**根本原因**：
- `god_model_max_tokens: 16384`（请求输出 token 数）+ 输入 prompt > 模型总上下文 16384
- God Model 生成 30 个地点时输出较大

**解决方案**：`config.json` 中 `god_model_max_tokens: 8192`

**日期**：2026-06-23

### ❌ 故障 5：Tool calling 未启用

**错误信息**：
```
"auto" tool choice requires --enable-auto-tool-choice and 
--tool-call-parser to be set
```

**根本原因**：
- Agentopia 使用 OpenAI 格式的 function calling（`tool_choice: "auto"`）
- vLLM 默认未开启自动工具调用解析

**解决方案**：`--enable-auto-tool-choice --tool-call-parser hermes`

> `hermes` 是 Qwen 系列通用的 tool call 格式

**日期**：2026-06-23

### ❌ 故障 6：period_weeks 不能整除 n_week

**错误信息**：
```
ValueError: period_weeks (10) must divide n_week (2) evenly
```

**根本原因**：
- 烟雾测试用 `--weeks 2`，但默认 `period_weeks: 10`
- 奖励计算每 N 周进行一次，N 必须整除总周数

**解决方案**：`config.json` 中 `period_weeks: 1`（或改为 `--weeks 10`）

**日期**：2026-06-23

### ❌ 故障 7：多 Agent 场景下上下文超支（待验证风险）

**错误信息**：
```
This model's maximum context length is 16384 tokens. However, you requested 
8192 output tokens and your prompt contains at least 8193 input tokens, 
for a total of at least 16385 tokens.
```

**发生阶段**：`signup_public_events`（公共活动报名），prompt = roleplay 上下文 + 本周公共活动列表

**根本原因**：
- `--max-model-len 16384` 限制总上下文 = 16K
- 单 agent 时 `signup_public_events` prompt 已膨胀到 8193 tokens
- 输出 8192 token → 总数 16385 > 16384
- 多 agent 场景 prompt 会更长（更多角色信息、更多公共活动）

**当前缓解**：`god_model_max_tokens: 4096`（给输入留 12K 空间）

**暑假跑正式实验前的风险**：
- 10 agent + 多公共活动 → prompt 可能超过 12K
- 16K 上下文可能不够用
- 但显存限制，提 `--max-model-len` 需同时提 `--gpu-memory-utilization`

**备选方案**（按推荐顺序）：
| 方案 | 命令 | 预期效果 |
|------|------|---------|
| A | `--gpu-memory-utilization 0.90` | 释放 ~0.5GB，KV cache 升至 ~4.3GB |
| B | A + `--max-model-len 20480` | 20K 上下文，覆盖大部分场景 |
| C | B + `--max-model-len 24576` | 激进方案，需验证显存 |

**建议**：暑假正式实验前，先用 3 agent × 1 week 跑一次上下文压力测试，确认不爆再跑长时间实验。

**日期**：2026-06-23

### ❌ 故障 8：Qwen3 thinking 模式耗尽输出 token

**错误信息**：
```
RuntimeError: Failed to generate locations via LLM after retries. Response: NO_RESPONSE
```
vLLM 日志显示模型持续生成 ~76 tok/s 但最终返回空响应。

**根本原因**：
- Qwen3-8B 有 `<think>...</think>` 思考模式
- 模型在 location 生成时大量输出思考内容，吃掉了 `god_model_max_tokens` 的全部配额
- 思考结束后没有剩余 token 输出实际 JSON
- `--reasoning-parser deepseek_r1` 不解决 token 预算问题

**临时缓解**：去掉 `--reasoning-parser`，靠 `god_model_max_tokens` 的绝对限制兜底

**长期方案**：
- location 生成已缓存（只跑一次），第二次运行直接从 `locations.json` 加载
- 如果重生成时再遇此问题，需在 prompt 中显式要求「不要输出 think，直接输出 JSON」

**日期**：2026-06-23

## 经验总结

### 不要做的事

1. **不要在新 GPU 上用最新 vLLM** — Blackwell (RTX 50 系列) 兼容性需要时间
2. **不要盲装 nvidia-cuda-nvcc-cu12** — 它当前是 CUDA 13，与 FlashInfer 不兼容
3. **不要删 `nvidia/cu13/` 目录** — PyTorch 需要其中的运行库
4. **不要相信降级一个版本能解决** — vLLM 0.20+ 都有 FlashInfer JIT 问题

### 应该做的事

1. **新 GPU（Blackwell）开发期用 vLLM 0.19.x** — 最后一个用预编译 cubin 的版本
2. **每次运行前确认 `period_weeks` 整除 `n_week`**
3. **God Model 输出 token 不要填满上下文** — 留一半给输入
4. **12GB 显存保守用 85% 利用率 + 16K 上下文 + 单并发**
5. **多 agent 实验前先跑上下文压力测试** — 3 agent × 1 week 验证不爆】

### 升级路径（未来）

当 FlashInfer 发布 Blackwell 兼容版本后：
1. 升级 vLLM 到最新版
2. 去掉 `--max-model-len 16384` 限制
3. 调高 `max_concurrency` 到 2+（视显存余量）
4. 上下文窗口可以放更宽

## 代码修复清单（论文贡献线① 工程适配）

> 以下修改均在 `03_Projects_项目记录/Agentopia/源码/` 中。WSL2 副本需同步：`cp /mnt/d/.../源码/<path> ~/agentopia/<path>`

### 修复 A：`god.py` — 公共活动关闭不生效

**文件**：`src/world/god.py`，`_generate_public_events` 函数

**问题**：`min_events = max(1, max_events // 2)` 在 `max_events=0` 时仍强制生成至少 1 个活动，用户的关闭意图被覆盖。

**修复**：在取 `max_events` 后立即检查：
```python
if max_events == 0:
    return []  # Public activities disabled
```

### 修复 B：`data_manager.py` — save_generation 对 string 类型 outputs 崩溃

**文件**：`src/agents/data_manager.py`，`save_generation` 方法

**问题**：函数签名声明 `outputs: List[Dict]`，但 vLLM 返回 400 后调用方传入 string。token 计数 (`m.get("content")`) 和 Markdown 写入 (`enumerate(outputs)`) 均对 string 报 `AttributeError`/`TypeError`。

**修复**：函数头部归一化：
```python
if not isinstance(outputs, list):
    outputs = [{"role": "assistant", "content": str(outputs)}]
```

### 修复 C：`role_agent.py` — compact 阶段用了错误的 max_tokens

**文件**：`src/agents/role_agent.py`，`_compact_response` 方法

**问题**：`generate_with_fc` 调用未传 `model_type="role"`，`_get_max_tokens_for_model` 落到默认分支返回 `god_model_max_tokens: 8192`。compact 时 input = 原始 prompt + outputs + compact 指令，远超 role model 阶段的 token 预算。8193 input + 8192 output = 16385 > 16384。

**修复**：加上 `model_type="role"` → 使用 4096 max_tokens。

### 修复 D：`role_agent.py` — compact 失败后 string crash

**文件**：`src/agents/role_agent.py`，`_compact_response` 方法

**问题**：`compact_output` 可能是 string（API 错误），但 `compact_output[-1]["content"]` 假定它是 list[dict]。触发链式崩溃。

**修复**：在 compact 后增加降级逻辑：
```python
if isinstance(compact_output, str) or (isinstance(compact_output, list) and len(compact_output) == 0):
    self.logger.warning("[COMPACT] compact failed, using original think_brief")
    return outputs[-1].get("content", "") if isinstance(outputs, list) and outputs else ""
```

### 修复 E：`utils.py` — vLLM 错误消息不被正则匹配

**文件**：`src/utils.py`，`generate_with_fc` 函数

**问题**：自动调整 max_tokens 的正则有两条 (`has N input tokens`、`passed N input tokens`)，但 vLLM 实际错误为 `your prompt contains at least N input tokens`。匹配失败 → 重新抛出异常 → 整个请求失败而非自动降级。

**修复**：加第三条正则：
```python
match = re.search(r"contains at least (\d+) input tokens", error_str)
```

### 修复 F：`config.json` — 小模型适配参数组合

**文件**：`config.json`

**关键变更**：
| 参数 | 默认值 | 适配值 | 原因 |
|------|--------|--------|------|
| `max_events_per_week` | 10 | 0 | 单 agent 无意义，且触发上下文超限 |
| `god_model_max_tokens` | 16384 | 8192 | 16K 总上下文，输出不能占满 |
| `role_model_max_tokens` | 16384 | 4096 | 留 12K 给日益膨胀的 role prompt |
| `max_concurrency` | 10 | 1 | 12GB 显存保守策略 |
| `period_weeks` | 10 | 1 | 必须整除 `n_week` |
| `role_model_max_tokens` | 16384 | **2048** | 2 周后 prompt 胀到 12790，4096 也超限 |
| `context_length` | 32768 | **16384** | 必须匹配 vLLM `--max-model-len`，否则自适应公式算错 |

### ❌ 故障 9：context_length 与实际 vLLM 限制不一致

**错误信息**：
```
max_tokens=19979 cannot be greater than max_model_len=max_total_tokens=16384
```

**发生阶段**：`_calculate_rewards` → `judge_others`（年终社交评分）

**根本原因**：
- 配置 `context_length: 32768`（Qwen3-8B 原生值），但 vLLM 限定 `--max-model-len 16384`
- 自适应降级公式：`adjusted_max = context_length - input_tokens - 500` = `32768 - 12790 - 500 = 19979`
- 19979 > vLLM 真实上限 16384 → 第二次请求仍然被拒

**解决方案**：`context_length: 16384`（与 vLLM `--max-model-len` 一致）

**日期**：2026-06-24

### ❌ 故障 10：extract_json 修复函数缺 model 参数

**错误信息**：
```
KeyError: 'model'
  File ".../utils.py", line 2246, in _fix_json
    model=kwargs["model"], ...
```

**发生阶段**：`judge_others` → JSON 解析失败 → 触发 `_fix_json`

**根本原因**：`_validate_ranking_response` 调用 `extract_json(response, **kwargs)` 时只传了 `known_names`，没有 `model`。JSON 修复失败时触发 `_fix_json`，尝试用 LLM 修复 JSON 但找不到 model。

**解决方案**：`_fix_json` 内检查 `"model" in kwargs`，缺失时直接返回原始 JSON 继续尝试解析。

**日期**：2026-06-24

### ❌ 故障 11：role prompt 随时间膨胀导致年末评分溢出

**错误信息**：
```
12790 input + 3595 output = 16385 > 16384 (差 1 token)
```

**发生阶段**：`_calculate_rewards` → `judge_others`（context_length 修复后）

**根本原因**：
- 经过 2 周模拟，角色 roleplay prompt 已膨胀到 ~12790 tokens（persona + 日记 + 他人印象 + 活动记录）
- `role_model_max_tokens: 4096` + 12790 = 16886 > 16384
- 自适应调整：`16384 - 12790 - 500 = 3094`，但仍不足且在边界附近不稳定
- 实际请求显示用了 3595 而非 3094（regex 匹配到的可能不是第一次错误）

**解决方案**：`role_model_max_tokens: 4096 → 2048`，12790 + 2048 = 14838 < 16384，留 ~1.5K 余量

**影响**：role model 输出被限制在 2048 token，可能截断长回复。暑假多 agent 实验时可能还需要进一步调整。

**日期**：2026-06-24

### ❌ 故障 17：judge_others JSON 解析失败导致年末 Reward 崩溃

**错误信息**：
```
RuntimeError: Failed to parse social ranking for Aaron Whitfield
```

**发生阶段**：`_calculate_rewards` → `judge_others`（20 周年末社交评分）

**根本原因**：
- Qwen3-8B 在生成 social ranking JSON 时，输出格式偶尔不规范
- `_generate_with_functions` 的 `format_validator` 仅在 `response_validation.enabled=true` 时生效

**解决方案**：`role_agent.py:1788-1791`，解析失败时兜底返回空 `SocialRanking`：

```python
if data is None:
    error_msg = f"Failed to parse social ranking for {self.name}"
    ERROR_LOGGER.error(error_msg)
    ERROR_LOGGER.error(f"Raw response: {response[:500]}")
    return SocialRanking(
        agent_name=self.name,
        time=str(self.clock.get_time()),
        affection_scores={},
        respect_scores={},
    )
```

**影响**：该 agent 的社交评分丢失，但不影响其他 agent 的评分计算和整体模拟完成。

**日期**：2026-06-27

## L2 压缩故障：③ 系统记忆验证阶段（2026-06-30）

> ③ 系统记忆代码（6/28 完成，~270 行）中包含 L2/L3 压缩功能。首次验证实验（R1）发现 L2 未生成任何文件，经排查在 `god.py` 的 `compress_events_to_l2` 和 `compress_l2_to_l3` 中连续发现 3 个 API 调用不对齐的 bug。

### 修复 H：`god.py` — compress_events_to_l2 中 get_world_setting 未定义

**文件**：`src/world/god.py`，`compress_events_to_l2` 函数

**错误**：`name 'get_world_setting' is not defined`

**问题**：函数内调用了 `get_world_setting(world_name)` 但未 import，并且调用结果 `world_setting` 从未被使用——属于死代码。

**修复**：删除 4 行死代码（`from src.config import get_config; config = get_config(); world_name = ...; world_setting = get_world_setting(...)`）。

**日期**：2026-06-30

### 修复 I：`god.py` — compress_events_to_l2/l3 中 messages 位置参数错误

**文件**：`src/world/god.py`，`compress_events_to_l2` 和 `compress_l2_to_l3`

**错误**：`_get_response() missing 1 required positional argument: 'messages'`

### ❌ 故障 18：OOM Killer — cache merge 内存溢出（16GB RAM）

**错误信息**：
```
1661 entries, no shards to merge
751 entries, no shards to merge
...
Killed
```

**发生阶段**：模拟全循环跑完后，`merge_run_cache()` 合并 LLM 缓存分片。

**根本原因**：
- `_merge_cache_file()` 调用 `pickle.load(f)` 把整个缓存文件一次性加载到 Python dict
- pickle 反序列化后内存膨胀 3-5×（Python 对象开销 > 序列化字节）
- 5 agent × 10 周 → 6 个缓存文件，最大 1661 条 LLM 响应
- 单个文件合并峰值 ~600MB × 6 ≈ 3.6GB，加上模拟本身 ~12GB → 超过 16GB 物理上限
- 进程被 Linux OOM Killer 杀掉后，正在写入的文件目录项已创建但 inode 数据未提交 → `ls` 能看到但 `file` 报不存在

**三合一修复**：

| 方案 | 改动 | 文件 | 行数 |
|:--:|------|------|:--:|
| **A** | `merge_run_cache(data_dir)` → `shutil.rmtree(run_cache_dir)`（跳过合并，直接删） | `run_world.py` | +5 |
| **A** | Ctrl+C 信号处理器同步改为删除 | `run_world.py` | +4 |
| **B** | `f.read()+pickle.loads()` → `pickle.load(f)`（流式反序列化） | `utils.py:_safe_load_pickle` | -2+1 |
| **B** | `del src_cache`（write 前释放）、`del shard_cache`（循环内释放） | `utils.py:_merge_cache_file, _merge_worker_caches` | +2 |
| **C** | `flush_all_caches()` 末尾 clear registries + `gc.collect()` | `utils.py:flush_all_caches` | +6 |
| **C** | `merge_run_cache()` 每文件合并后 `gc.collect()` | `utils.py:merge_run_cache` | +2 |

**为什么之前没触发**：3 agent 实验最多 ~800 条/文件，5 agent 翻倍到 ~1600 条，刚好踩过临界点。

**日期**：2026-07-04
