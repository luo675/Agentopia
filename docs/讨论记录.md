## 2026-06-25：烟雾测试通过 + T1 完成 + T2 方向确定

### 烟雾测试修复（3 个源码 bug）

1. **Qwen3 thinking 模式吃光输出 token**：`utils.py:1137-1141`
   - Qwen3 默认启用 `<think>` 推理，Location 生成时 2048 token 全被 thinking 占用，JSON 一个字没输出 → `NO_RESPONSE`
   - 修复：始终显式传递 `chat_template_kwargs={"enable_thinking": False}`
   - 这是 397B→8B 降级暴露的问题：大模型不需要关 thinking 也能在 token 预算内完成

2. **context_length 16K 不够**：`config.json`
   - Week 2 Reward 阶段 prompt 累积到 14838 token，输出 1547 → 16385 > 16384 → 400 BadRequest
   - 修复：`context_length: 16384 → 20480`，`max-model-len` 同步

3. **Profile Update 失败时 TypeError**：`god.py:2216`
   - `get_response_with_retry` 失败返回字符串 `"NO_RESPONSE"`，但 `update_yearly_profile` 只检查了 `None`
   - 大模型从不触发这个路径，8B 在生成复杂人格 JSON 时不稳定
   - 修复：`is None → not isinstance(new_profile, dict)`

## 2026-06-27 下午：T3-A 结果 — 随机化 prompt 大幅减少冻结

### 实现

- 修改 `prompts.py`：新增 `REFLECTION_QUESTIONS` 列表（10 个具体问题）+ `build_review_prompt()` 函数，每次随机抽 3 个

| **Vale** | W5 冻结，6 周逐字重复 | 短语级重复 | **完全无冻结** ✅ |

### 结论

**随机化 prompt 是三种方案中效果最好的。**

- T3（2048 固定）：3/3 全冻，冻得最彻底
- T3-B+T4（4096 固定）：0/3 全冻，但 2/3 有短语级重复
- T3-A（4096 随机）：1/3 短暂冻了 2 周后恢复，另外 2 个完美通过

关键推论：**Reflection 冻结的主要诱因是固定 prompt 诱导的模式坍缩，而非 8B 模型容量不足。** 随机化是低成本、高收益的干预——不改架构，几行 prompt 随机化让冻结率从 3/3 降至 1/3。

## 2026-07-02 下午：⑤ 健康系统设计

### 决策

1. **混合评估**：可量化事件用 Python 规则兜底，主观事件用 God LLM 每周评估（复用 ③ 的 `get_response_with_retry` 调用模式）
2. **显式规则**：新增 `HEALTH_RULES` prompt，约束 LLM 只能判范围、不能乱给分
3. **人格调制**：从现有 traits（responsibility/control/judging → health_consciousness；confidence/patience → emotional_stability；extraversion/introversion → social_seeking）派生，不新增 persona 字段
4. **模糊感知**：agent 感受的是自然语言（"你最近很疲惫"），不给具体数字。措辞强度由人格派生值调制
5. **NIGHT 不睡可补觉**：God 健康评估查看当天全部 4 时段活动，做整体判断

## 2026-07-04 早：T6 快测首跑 — OOM Killer

### 现象

5ag × 10wk，~4h，全循环跑通（`Total reward: 5 agents`），但最后阶段被 Linux OOM Killer 杀掉：

```
1661 entries, no shards to merge
751 entries, no shards to merge
...
Killed
```

数据直接写在 `data/` 根目录下（非 `data/apartment_XXXXX/` 子目录），文件系统 dentry cache 残留导致 `ls` 能看到但 `file` 报不存在——数据全部丢失。

### 根因

`merge_run_cache()` 在进程退出前合并 LLM 缓存分片。实现方式：`pickle.load()` 把整个缓存文件一次性加载到 Python dict，反序列化后内存膨胀 3-5×。6 个缓存文件（最大 1661 条），每个峰值 ~600MB，加上模拟本身占 ~12GB，踩过 16GB 物理上限。

### 修复：三合一内存优化

| 方案 | 改动 | 文件 |
|:--:|------|------|
| **A** 跳过合并 | `merge_run_cache(data_dir)` → `shutil.rmtree(run_cache_dir)` | `run_world.py` |
| **A** 信号处理器 | Ctrl+C 路径同步改为删除（初版遗漏，review 发现） | `run_world.py` |
| **B** 流式反序列化 | `f.read() + pickle.loads()` → `pickle.load(f)` | `utils.py:_safe_load_pickle` |
| **B** 提前释放 | `del src_cache` 在 write 前、`del shard_cache` 在循环内 | `utils.py:_merge_cache_file, _merge_worker_caches` |
| **C** 显式 GC | `flush_all_caches()` 末尾 clear registries + `gc.collect()`；`merge_run_cache()` 每文件合并后 `gc.collect()` | `utils.py` |

源码改动 ~20 行。详见 [[故障记录#故障18]]。

### Review 发现纰漏

初版只改了正常退出路径，**Ctrl+C 信号处理器仍调用 `merge_run_cache()`**——review 时发现并修复。

### 故障 19：model_assignment.json 缺失 NPC 导致 resume 失败

**错误**：`ValueError: model_assignment.json missing agents: ['Alex Medina', ...]`（95+ 个 NPC）

**根因**：首次启动时 `_load_or_assign_models` 给所有 agent（含 NPC）生成了分配。但 checkpoint 只保存了 5 个活跃 agent。resume 时检查到缺失 → 抛异常。

**初始修复（错误）**：用 Python 脚本补全 95+ NPC 到 model_assignment.json。虽然过了检查，但这让 NPC 也走了完整 LLM 初始化路径，可能拖慢 Contact 阶段。

**最终修复**：改 `world.py:_load_or_assign_models`，resume 时缺人自动补默认值而非报错。只保留 5 个活跃 agent 在 model_assignment.json 中。

### 故障 20：W40+ prompt 膨胀导致频繁 token 超限重试

**错误**：`BadRequestError: 17398 input + 3083 output = 20481 > 20480`

**根因**：52 周后期，agent 的 roleplay prompt 累积了 persona + layered_memory(L1+L2) + health_context + schedule + contact_history，单次调用 prompt 接近 20K 天花板。自适应降级机制在工作但每次重试增加延迟。

**影响**：W40 之后实际耗时远超线性推算。这是论文的核心发现——20K 上下文是消费级 GPU 上 5 人模拟的真实天花板。

### 故障 21：vLLM 返回字符串而非标准列表格式

**错误**：`TypeError: string indices must be integers` at `utils.py:1792`

**根因**：`_get_response` 中 `out[-1]["content"]` 假设 `out` 是 `List[Dict]`，但 vLLM 在 encounter 生成时偶尔返回 plain string。

**修复**：`utils.py:1791` 加类型检查——`isinstance(out, str)` 时包装为标准格式。

### 诊断过程

Run1 W41 后极慢（每周 ~14h），日志反复出现：



### 根因分析

拆解 W40 的 roleplay_prompt 后发现：③ 分层记忆只占 ~2860 tokens。真正的膨胀源是：

| 组件 | 占 token | 问题 |
|------|:--:|------|
| scratchpad（人物笔记） | ~6000 | character_limit=50，加载 50 人全量笔记 |
| contact_history（聊天记录） | ~3000 | 3 周原文 + 重复加载 scratchpad 摘要 |
| **社交知识合计** | **~9000** | 与 ③ 的衰减原则矛盾 |

### 核心矛盾

③ 让事件随时间衰减（L1→L2→L3），但**人物笔记和聊天记录永不衰减**。一个 agent 的大脑里有两套规则——这是一个设计盲点。现实中的记忆是整个一体衰减的：你既不会记得 40 周前每天做了什么，也不会记得 40 周前跟某人的对话细节。

### 修复：社交知识衰减优化

| # | 改动 | 文件 | 效果 |
|:--:|------|------|------|
| 1 | list_scratchpads character_limit 50→20 | data_manager.py | 只显示最近互动的 20 人 |
| 2 | read_message 删除重复 scratchpad 摘要加载 | data_manager.py | 去重（roleplay_prompt 已加载） |
| 3 | read_message 消息窗口 cap 为 2 周 | data_manager.py | 3→2 周 |
| 4 | roleplay_prompt 调用显式 character_limit=20 | data_manager.py | 对齐改动 1 |

改动 ~30 行，单文件。W40 prompt 估算从 ~17K 降至 ~11K。
