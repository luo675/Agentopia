# 代码改进计划：三轮迭代

## 迭代总览

```
第一轮 ③ 系统记忆         ~150 lines    4h 验证    改 data_manager / prompts / role_agent
第二轮 ④ 24h 时间下钻     ~150 lines    4h 验证    改 clock / scheduling / prompts / role_agent
第三轮 ⑤ 健康系统         ~250 lines    4h+4h 验证  改 role_agent / prompts / world / reward
第四轮 T6 全组合           ~0 lines      10h        跑 5ag × 52wk
```

每轮改完 → 跑 T3 规模（3ag × 10wk）对比基线 → 拿到数据 → 讨论分析 → 进入下一轮。

## 第一轮：③ 系统记忆（agent 不写日记，God 做三层压缩）

### 核心思路

**现状问题：**
- Agent 在 Review 阶段写 weekly diary → 系统把 diary 喂回给 agent → 5 周后丢弃
- 矛盾：agent "写了日记" 但 "忘了"，认知上说不通

**改进：**
- Agent **不写日记**。Review 只做反思（Reflection），不输出 Summary（系统从事件日志自动生成）
- 系统自动维护每个 agent 的**事件日志**（event_log）：今天做了什么、见了谁、结果如何
- God 模型在每个 W6 到来时，将 W1 压缩为 ~200 字要点（L2）；W21 到来时将 L2 要点再压缩为 ~50 字里程碑（L3）
- Agent 的 Plan/Review 阶段接收的是「你记得什么」而非「你的日记写了什么」
- 三层记忆：L1（1-5 周，完整）+ L2（6-20 周，要点）+ L3（21 周+，里程碑）

## 第二轮：④ 24h 时间下钻（每天 4 时段，自主作息）

### 核心思路

**现状问题：**
- WORLDVIEW 描述：每天 1 个 free time slot → agent 每周做 Plan → 每天执行相同活动
- agent 的 5 天行为几乎一样，没有作息节奏

**改进：**
- 每天分为 4 个时段块：NIGHT（00-06）、MORNING（06-12）、AFTERNOON（12-18）、EVENING（18-24）
- Agent 在 Plan 阶段为每天各时段做计划
- NIGHT 时段：agent 决定几点睡、熬夜做什么（如果需要）
- MORNING 时段：agent 决定几点起床、赖不赖床、上午做什么
- 一天可以做 2-4 件不同的事（vs 现在的 1 件）
- 不同 agent 展现出不同的作息模式（夜猫子 vs 早起型）

### 设计选择：轻量方案（不改引擎循环）

保持 `n_day` 活动循环不变，**只改 Plan 的语义 + 增加每天的 solo 活动数量**。

具体做法：
- Plan 阶段：agent 输出「每天各时段做什么」的计划
- Activity 阶段：引擎仍然是每天循环，但每天内循环 2-3 个次要 solo 活动（如果计划了多个）
- 不需要新增引擎级时间状态（day 已经够用，时段只是 prompt 层面的概念）
- 不需要改 clock.py

## 第三轮：⑤ 健康系统（身心指标 + 极端行为）

### 核心思路

**现状问题：**
- 只有 vitality（体力）和 fulfillment（四维满意度），没有真正的"生命风险"
- Agent 永远不会生病、不会因为心理问题做出极端行为
- 原论文的 "生命奖励" 追求幸福最大化，但没有定义"不幸福的代价"

**改进：**
- 新增 `physical_health`（0-100）和 `mental_health`（0-100）两个独立指标
- 身体健康受睡眠、饮食、运动影响
- 心理健康受事件冲击影响（好事+、坏事-），且持续衰减
- mental_health 低于阈值（如 < 20）持续 N 周 → 可能出现轻生行为
- physical_health 低于阈值（如 < 10）→ agent 可能病倒甚至死亡
- 这个系统让模拟更像真实社会——不仅有"追求幸福"，也有"避免悲剧"

### 改动文件

#### 1. `src/agents/data_manager.py` — ~50 lines

```
新增 state 字段：
  physical_health: int = 80  # 0-100, 起始健康良好
  mental_health: int = 70    # 0-100, 起始心理正常

新增方法：
  get_health() → dict
  update_physical_health(delta: int)  # 外部事件触发
  update_mental_health(delta: int)    # 外部事件触发
  get_health_history(n_weeks) → list  # 健康历史（给 reward 计算用）
```

#### 2. `src/agents/prompts.py` — ~50 lines

```
新增：
  HEALTH_SYSTEM_PROMPT — 给 agent 描述健康系统的 prompt

  SLEEP_EFFECTS — God eval prompt 新增：
    睡眠不足 → physical_health -X, mental_health -Y
    充足睡眠 → physical_health +X
    
  EVENT_IMPACT — God eval prompt 新增：
    社交冲突 → mental_health -5 to -15
    被他人感谢/认可 → mental_health +3 to +10
    失去亲人/被开除 → mental_health -20 to -40
    达成重要目标 → mental_health +10 to +20

改：
  REVIEW_PROMPT — agent Reflection 中可能提及最近的心理感受
    但不强制要求 agent "汇报" 健康数据（健康是系统计算的，不是 agent 自觉的）
```

#### 3. `src/agents/role_agent.py` — ~60 lines

```
改：
  init：加载初始 physical_health / mental_health

  settle_week() 结尾：
    计算本周健康变化：
      - 每晚睡眠 < 6h → health -5 per night
      - 每天饮食正常 → health +1
      - 事件冲击由 God eval 在活动评价时一并计算

新增：
  _check_life_crisis() → 在每周 settle 后检查：
    if mental_health < 20 for 4 consecutive weeks:
      → 概率触发 "轻生" 事件（在 Plan 阶段的 prompt 中注入极端负面思考）
    if mental_health < 10 for 2 consecutive weeks:
      → 确定性触发 "轻生" 事件
    
    if physical_health < 10 for 3 consecutive weeks:
      → agent 标记为 deceased
      → agent 不再参与后续周的 Plan/Contact/Activity
      → 在社交网络中标记为 "已去世"（其他 agent 可以对此做出反应）
```

#### 4. `src/world/world.py` — ~30 lines

```
改：
  step() 中：
    如果 agent 已去世 → 跳过该 agent 的所有阶段
    Plan 开始前广播「去世消息」给社交网络中的其他人（通过 msg_center）

  settle_week() 后：
    调用 _calculate_health_deltas() 系统计算健康变化
```

#### 5. `src/world/reward.py` — ~40 lines

```
新增：
  compute_health_penalty() → 将健康数据整合进 subjective reward：
    如果 physical_health < 30 或 mental_health < 30：
      → subjective reward 额外扣分（代表生命质量下降）

改：
  compute_subjective_rewards()：
    读取 health_history → 将健康维度纳入 misery penalty 计算
```

### 验证指标

- Agent 间健康水平差异（是否有些 agent 更健康）
- 是否有 agent 触发了 mental_health 低阈值 → 极端行为出现率
- 极端行为对社交网络的影响（其他人是否做出反应）
- 健康系统是否让模拟行为更"严肃"（agent 不只是追求快乐，也要维持生存）

## 执行原则

1. **每轮改完 → 跑实验 → 看数据 → 记录发现 → 再改下一轮**
2. **config.json 中的 role_model_max_tokens 保持 4096，Review prompt 随机化保持（T3A 确认的有效改进）**
3. **遇到不可预期的 bug → 回退上一轮改动 → 分析原因 → 重新设计**
4. **每轮实验数据保存在 `实验数据/{轮次}-{日期}-{描述}/` 下**
5. **⚠️ 新增 LLM 调用代码的硬规则**（2026-06-30 复盘确立）：
   - **写之前**：先看 1 个现有 `get_response_with_retry` 调用，照着抄签名
   - **写完后**：立刻在 WSL2 跑 `python -c "from src.world.god import compress_events_to_l2; print('OK')"` 验证导入
   - **核心原则**：不要凭记忆写 API，去代码里看实际怎么调的
   - **写代码当天**必须至少跑一次编译验证，不得攒到第二天
   - 背景：R1-R4 四个 Bug 全都源于同一个错误——AI 凭空编造了不存在的 API 调用惯例
